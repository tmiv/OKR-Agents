Why the message was garbage

service/validate.js was right there. BuildKit resolves every context COPY in a Dockerfile eagerly and in parallel, so when the wrong context makes several of them fail, it reports an arbitrary one. It happened to name a file that exists relative to your shell — pointing away from the real problem.

The correct command was in the Dockerfile header, but a header comment is not where anyone looks after typing docker build .:

docker build -f service/Dockerfile -t okr-viewer-service .

The fix

I tried two cheap guards first and both lost the race — reordering the COPYs so the lockfile is read first, and gating each stage on a bind-mount check stage. The opaque error still won each time. The only thing that works is structural:

A single ctx stage (FROM busybox:1.37 + COPY . /ctx) is now the only reader of the build context. It checks for package-lock.json and schema/; every other stage pulls named paths --from=ctx or --from=build. One context read can't be raced, so now you get:

  Wrong build context: no package-lock.json and no schema/ in it.

  This image builds from the repo root. One lockfile covers all
  three workspaces, and service/ imports @okr-viewer/schema, so
  neither is reachable from a service/-scoped context.

      docker build -f service/Dockerfile -t okr-viewer-service .

This costs nothing in layer caching, which I checked rather than assumed: after a real content change to service/index.js, both npm ci layers stayed CACHED and only the source COPY reran. BuildKit keys a COPY --from on the content of the paths named, not on the source stage's layer.

No. SERVICE_URL must be a bare origin — scheme://host[:port], no path, not even a trailing slash. I measured all four forms rather than trusting the docs:

SERVICE_URL service receives
http://service:8787 /api/health 200
http://service:8787/ /health 404 Cannot GET /health
http://service:8787/api /apihealth 404
http://service:8787/api/ /api/health 200, by coincidence

The rule: location /api/ passes the request URI through only when proxy_pass has no URI part of its own. Give it one — a bare / counts — and nginx substitutes it for the matched /api/ prefix rather than appending.

Why this needed more than a doc note

The mistake is invisible from outside. nginx keeps serving the app, and the web container's healthcheck only asks for /, which is static — so the container reports healthy while every chat turn 404s. Same quiet-failure shape as a wrong APP_ORIGIN, where /api/health stays green because it sends no Origin.

So I added web/docker-entrypoint.d/10-check-service-url.sh, which runs before nginx renders the template and refuses to start on anything else:

[web] SERVICE_URL="http://service:8787/" — it has a path or a trailing slash, which nginx would substitute for the /api/ prefix
[web] It must be a bare origin: scheme://host[:port], no path, no trailing slash.
[web]   SERVICE_URL=http://service:8787

Verified against a trailing slash, a path, a missing scheme, and the good value — which now logs SERVICE_URL=http://service:8787 — /api/ will proxy there with the path preserved at boot, so the config is visible in the logs either way. I also made SERVICE_URL overridable in compose (${SERVICE_URL:-http://service:8787}) to match how APP_ORIGIN already worked.

One caveat

Compose has restart: unless-stopped, so a bad SERVICE_URL becomes a crash loop rather than a clean stop — it prints the error on every attempt, and docker compose up --wait will sit until its timeout. That's the tradeoff for production resilience; say the word if you'd rather it be on-failure.

The distinction you may be probing

The Svelte app never sees SERVICE_URL. It calls a relative path — fetch('/api/chat') at App.svelte:186 and :388 — and I confirmed the built bundle contains /api/chat and zero occurrences of http://service:8787 or SERVICE_URL.

That's by necessity, not preference: vite build produces static files, so anything baked into the bundle would be fixed at build time and public in the browser. Keeping the call relative is what makes SERVICE_URL a runtime knob — one image, repointed per environment — and what keeps the browser same-origin so ANTHROPIC_API_KEY never leaves the service container.

So the answer depends on what "the main app" means:

  • The web container — yes, SERVICE_URL is load-bearing. Break it and /api/ breaks (that's what the new entrypoint guard catches).
  • The browser bundle — no, and it must stay that way. If you ever want the browser to call the service directly instead of through the proxy, SERVICE_URL would not do it; that needs a Vite build-time variable (import.meta.env.VITE_*) and a rebuilt image per environment — and then the CORS work from the last turn stops being defence-in-depth and becomes the actual boundary.

One caveat on my evidence: I couldn't show a service-side access log line for the proxied request, because the service only logs /api/chat turns, not /api/health. The 502-when-stopped test is the stronger proof anyway — it isolates the hop.
