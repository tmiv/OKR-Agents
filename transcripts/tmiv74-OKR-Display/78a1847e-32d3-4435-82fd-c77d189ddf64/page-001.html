Fixed. Your instinct about a feedback loop was right, though hover was never selecting anything — the loop was in Svelte's dependency tracking.

What was happening

Graph.svelte:259 is the effect that pushes tree data into the force graph. Its last line read hovered:

if (hovered) hovered = graph.graphData().nodes.find(...) ?? null;

That read is tracked, so hovered became a dependency of the effect. Then:

  1. Pointer enters a node → after the 150 ms delay, hovered = n.
  2. The data effect re-runs and calls graph.graphData(...).
  3. three-forcegraph treats that as new data: .stop().alpha(1) — an explicit re-heat — then runs the 80 warmupTicks synchronously (three-forcegraph.mjs:1414, :1476).
  4. The whole tree jumps, the node leaves the cursor, hover clears to null — which is another write to hovered, so it re-heats again.

I measured the jump in the running app: one graphData() round moves nodes up to 54.5 world units.

The fix

One untrack in Graph.svelte:259, so the effect depends on tree alone while the hovered-node re-point still happens on real edits:

untrack(() => {
  if (hovered) hovered = graph.graphData().nodes.find((n) => n.id === hovered.id) ?? null;
});

Verified in the browser

Hovered a node in the live app with the real pointer: the card came up with the correct content ("Win and expand mid-market accounts efficiently") and max node displacement across all 27 nodes was 0.0000 over 3 seconds. npm test passes (9/9); build is clean.

Hover was already highlight-only — onNodeHover only sets hovered for the card; onSelect fires on click. So no behavioural change was needed there.
