Fixed. The jitter was the camera being teleported six times a second during the startup framing sequence.

Cause

frameWhenSettled() follows the expanding layout by re-framing every 150 ms with a 900 ms flight, on the assumption (stated in the comment at Graph.svelte:230) that each call retargets the tween in flight. It doesn't. force-graph's setter, at three-render-objects/dist/three-render-objects.mjs:320, does:

// cancel any ongoing pov animation
state.povPosTween?.end();

and tween.js's end() fast-forwards rather than cancelling — update(this._startTime + this._duration). So each look first snapped the camera onto the previous look's target, then eased from there. At 150 ms into a 900 ms Quadratic.Out tween the camera is ~31% along, so every one of the 16 looks teleported it the remaining ~69%. That's the jitter, and it settled only because the last look had no successor to snap it.

Verified in the running app before touching anything — one framing move, then a retarget, reading the camera position synchronously either side of the second call:

position
start 400.0, 301.5, 739.4
target of move 1 800.0, 601.5, 939.4
immediately after retargeting to a different point 800.0, 601.5, 939.4

The camera landed 0.04 units from the target it was supposed to be abandoning, before move 2 had rendered a single frame.

Fix

Graph.svelte now runs its own camera tween instead of the library's, alongside the camera.up tween that was already hand-rolled there — same Quadratic.Out easing, same aim-swings-in-a-third-of-the-flight behaviour, but from is always the live camera position, so a retarget bends the path rather than jumping it. frame() records the tween (Graph.svelte:185); animate() applies it (Graph.svelte:283). Nothing calls graph.cameraPosition() as a setter any more.

Verification

  • The same probe against the patched build, retargeting a real in-flight f-key framing move mid-flight: teleport distance 0.000 — camera at 662.3, 497.5, 662.3 before and after the retarget.
  • Dataset swap to the 135-node tree runs the full settle path and still lands framed and centred, pulling back progressively across frames.
  • npm test — 16 pass; vite build clean.

One thing I noticed and left alone: at mount, graphData() is set twice — once in onMount (Graph.svelte:356) and again on the initial run of the $effect at Graph.svelte:370 — so the simulation re-heats and runs its 80 warmup ticks twice. Both happen before first paint, so it's wasted startup work rather than a visible symptom, and it isn't part of this bug.

Both done, plus a third defect the drag investigation turned up.

1. Double graphData at mount

onMount seeded the data and the $effect pushed the same tree again on its first run, re-heating the simulation to alpha 1 and burning a second set of 80 warmup ticks. Guarded with an applied field recording what the graph already holds (Graph.svelte:55, :449).

Verified by counting setter calls: an unrelated reactive update (team-labels toggle) now pushes 0 times, a document swap pushes exactly 1.

2. First-drag jitter

Two separate causes, both real.

The startup framing sequence doesn't yield to the mouse. frameWhenSettled() runs 16 looks over 2.4 s, and the last flight lands ~3.3 s after load. Every look re-aims the camera, re-levels camera.up and resets the distance — and those writes land on top of whatever the drag is doing, six times a second. Grab the model inside that window and the camera is pulled back to the framing every frame. It's the first drag only because the sequence has run out by the second one. Same root as the bug you already had, so your hunch was right: it's the settle loop both times.

Fixed by releasing the camera the moment the user takes the controls — force-graph's controls emit start on pointer-down for rotate, pan and zoom alike (Graph.svelte:281, :412).

Verified: a 556-unit framing flight interrupted mid-air by a pointer-down, then several more rendered frames — camera moved 0.00 further.

TrackballControls was measuring the wrong canvas. It reads the element rect once in its constructor and force-graph never re-measures. That reading happens before the stage is laid out, so it captured the renderer's default 600×300 at the wrong origin while the real canvas is 900×665.
